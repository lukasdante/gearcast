# GearCast capture environment

A local copy of the GearCast app for the promo-video Playwright captures. It runs the same Worker code and
the same app build as production (version db7b792b, the current working tree), with its own local state. It
never writes to production.

## Commands

```bash
video/capture/up.sh             # build app → video/capture/.dist, seed if no state yet, start wrangler dev
video/capture/up.sh --no-build  # start with the existing build
video/capture/reset.sh          # stop, wipe .state, reseed, start, pre-render the 30 history PDFs (~16 s)
video/capture/reset.sh --build  # same, and rebuild the app first
video/capture/down.sh           # stop (keeps state)
node video/capture/scripts/story_state.mjs   # print what the dashboard and APIs show right now (read-only)
node video/capture/scripts/smoke.mjs --reset # API checks of every story write per role, then reset
```

- **URL:** http://127.0.0.1:8790. The port is fixed; override it with `CAPTURE_PORT`. The inspector port is 9240.
- **Log:** `video/capture/.state/wrangler.log`.
- Run `reset.sh` before every take. All D1 and R2 state goes back to the seed: approvals, assignments,
  access grants, scans, incidents, uploads, usage counters and PDFs.
- Use a **fresh browser context** for each take and each role. The app keeps simulated faults, engineer
  layout drafts, PM assignment caches and plant layouts in `localStorage`, and `reset.sh` cannot clear those.
  `lib.mjs` → `newStoryContext()` does this for you.

## Isolation (no production writes)

`wrangler.jsonc` here is a capture-only config, and every command uses `--local --persist-to video/capture/.state`.

| Binding | Mode | Notes |
|---|---|---|
| DB (D1) | local | Fake database id `…ca97`, so an accidental `--remote` cannot reach `gearcast-db`. |
| FILES (R2) | local | Bucket `gearcast-capture-files`, which does not exist remotely. |
| AI (Workers AI) | **remote** | Inference only: query embeddings for KB search and Upload. |
| VEC (Vectorize) | **not bound** | Search never used it. Upload and delete call `VEC.upsert/deleteByIds` inside try/catch, so they fail harmlessly and nothing is indexed remotely. |
| Secrets | `.dev.vars` | Generated by up.sh from `worker/.dev.vars`: `DEEPSEEK_API_KEY` and `AUTH_SECRET`, plus `DEV_MODE=1`. **No `ADMIN_TOKEN`**, so `/api/admin/seed` answers 403. |

- **KB vectors.** Dense search ranks against `index/builtin-v4-423.f32`. `seed.sh` downloads it once from
  production R2 (a read-only GET) into `.cache/` and puts it into local R2. Health shows `kb_ready: true`.
- **Deploy guard.** The config has no routes, no custom domain and `workers_dev: false`, so it cannot replace
  the live site.
- **Quotas are local.** The daily caps from `wrangler.jsonc` count in local D1, and `reset.sh` zeroes them.
  Caster (DeepSeek) and embeddings still cost real API calls.

## Upload paths for the illustration PNGs (`video/public/illustrations/`)
All accept PNG, either with `accept="image/*"` or by sniffing magic bytes on the server.

| Where | Client handling | Server limit |
|---|---|---|
| Caster photo (paperclip → "goes into an incident report as Photo 1") and Incidents → photos | Re-encoded to **JPEG ≤ 1600 px, q 0.82**. Transparency becomes white. | JPEG/PNG, **3 MB** each after re-encode, **max 4** per report |
| PM findings photos | Same re-encode | JPEG/PNG, **4 MB** each, **max 6** |

## Date shift and reproducibility
- The data is cut off on 2026-10-31. Both the Worker (Manila clock) and the app (browser clock) shift every date
  by `today − 2026-10-31`. Readings, statuses, rankings and trend values are therefore **the same on any day**,
  and only absolute dates and weekdays move.
- **What differs between takes on different days:**
  - every printed date ("Data as of", trend axis labels, incident dates, `expires_at`)
  - the **dashboard PM calendar grid**, where the "today" cell and the due-date dots move. From 1 Dec it shows
    December.
- **What differs within one day (time of day):**
  - Incident trends (Field 3) and the PM page include only readings up to "now". P-101B's daily check for today
    is logged at 10:00, and manual rounds come several times a day.
  - The 7-day P-101B summary, for example, is "1.5 → 1.6" at 09:00 and "1.5 → 1.5" at 14:00.
  - "Data as of HH:MM" ticks live.
- **Fix: pin a story clock.** `lib.mjs` → `newStoryContext()` pins both clocks to `AS_OF` (default
  `2026-11-28 14:00`, override with `CAPTURE_AS_OF`):
  - It sends `x-gearcast-as-of` on every request. The Worker honours it because `DEV_MODE=1`, on the capture
    server only.
  - It installs Playwright's clock in the page. Time keeps running, so 3D animations work.
- With the pin, **re-takes on any day are identical**, the 3D included. Without it, re-takes must be on the same
  day and in the same part of the day. Keep the pin after 10:00.
- Caster and troubleshooter wording comes from DeepSeek and is never identical between takes. Numbers come from
  tools and are stable.

## Capture gotchas and stable selectors
- **Login.**
  - Steps: `getByRole('tab', { name: 'Supervisor' | 'Engineer' | 'Technician' })`, then
    `.login-card select` → `selectOption('MT-02')`, then `.login-card input[type=password]`, then
    `.login-card button[type=submit]`.
  - The session is an HttpOnly cookie that lasts 12 h. One context per role.
- **Splash.** After login the GLB preload screen holds the app. Wait for `.splash` to be **detached**, not
  hidden. It has a 700 ms minimum and a 450 ms fade, and gives up after 20 s at most. It was measured at about
  3.1–3.5 s from submit to dashboard on a cold headless start.
- **3D (WebGL).**
  - Headless Chromium needs `--use-angle=swiftshader --enable-unsafe-swiftshader`; `lib.mjs` → `launch()` adds
    them.
  - Canvases are `.dash-3d canvas` (dashboard; it auto-rotates) and the Plant Overview canvas.
  - After the splash, models are cached. The Overview Inspector appeared about 2 s after "On plant". Wait for
    `button:has-text("Simulate fault")`, then give the scene a few frames to settle.
- **Dashboard.**
  - Pager: `.dash-pager button` hasText `P-101B`.
  - Card actions: `.dash-att button` hasText `On plant` | `Asset details` | `Troubleshoot`. "On plant" opens
    Plant Overview with that asset selected; this is the easy way to select an asset without clicking a mesh.
  - Process stages: `.dp-node` (+ `.down` / `.affected` / `.changeover`).
  - Reasons: `.dash-reasons li`. KPIs: `.dash-kpi`.
- **Inspector.**
  - Buttons by text: `Simulate fault`, `Clear`, `Troubleshoot`, `Switch duty to P-101A`.
  - Cost box: `.cost-box` (`.down` when the plant is impacted), with outage input label `Expected outage (h)`.
- **Routes** are hash routes: `#/dashboard`, `#/overview`, `#/assets`, `#/pm`, `#/spares`, `#/incidents`,
  `#/troubleshoot`, `#/rr`, `#/knowledge`, `#/labels`. There is no Approvals route: the queues live on
  PM / Spares / Overview.
- **Caster.**
  - Open it with `button[aria-label="Ask Caster"]`. Attach with `button[aria-label="Attach photo"]` plus the
    hidden `input[type=file]` next to it; use `setInputFiles`. Send with `button[aria-label="Send"]`.
  - Answers stream (SSE), with tool chips first. Wait for the send button to be enabled again, which means
    busy → idle.
- **PM.** Assign with `select[aria-label="Assign PM-02 P-101B"]`, then `selectOption('MT-02')`. Search box:
  `input[aria-label="Search PM tasks"]`.
- **QR scan.**
  - `localhost` is a secure context, so the live camera works with Chromium's fake-camera flags.
  - Labels encode `https://<origin>/asset/<ID>` or `gearcast://asset/<ID>`. The manual field also accepts
    `P-101B` or `QR-P-101B`.
- **PDFs** (manual page, incident report) open as PDF responses. The headless shell has no PDF viewer, so record
  those beats headed or with the `chromium` channel, or show the PDF in the edit.
- **Writes during a take** (approvals, grants, incidents, assignments) persist until `reset.sh`. Order the beats
  or reset between them.
